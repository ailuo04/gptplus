# gpt++ v1.2.5

## 更新内容

### 修复：走 OpenAI 兼容中转时 Codex 请求全部失败

在 Codex Desktop 里选择经 gpt++ 注入的中转模型（例如 `deepseek-flash`）发消息，一轮都发不出去，直接报错：

```
Invalid schema for function 'list_mcp_resources': null is not of type "array"
```

原因：

- Codex Desktop 每轮请求都会带上内建工具 `list_mcp_resources` / `list_mcp_resource_templates`。这两个工具没有必填参数，codex-rs 侧用 `JsonSchema::object(properties, /*required*/ None, ...)` 描述，序列化后 `parameters.required` 就是 `null`。
- OpenAI 官方端点容忍这种写法；但按 JSON Schema 元模式严格校验的 OpenAI 兼容中转（尤其内部还会再把 chat 转成 Anthropic 格式的）会直接返回 400，整轮请求失败。
- 网关此前对这类工具是整对象透传，没有做任何归一，所以只要走这类中转就百分百复现，与用户问的是什么无关。

修复：

- 新增 `toolParameters()`（`src/core/gateway/responses.js`），openai 与 anthropic 两个适配器的工具转换统一走它。
- 递归去掉值为 `null` 的 schema 关键字（`required: null`、嵌套属性里的 `type: null` 等）。数组元素中的 `null` 是数据而不是关键字（例如 `enum` 的取值），保留不动。
- 补齐顶层的 `type` / `properties` / `required`。实测该中转在 `required` **缺失**时同样会补成 null 并报同一个错，所以只删空值不补默认值仍然修不好。
- chat 形状（`{type:'function', function:{…}}`）的工具不再整对象透传，改为浅拷贝并清洗 `parameters`，其余字段（如 `strict`）原样保留。

判定依据（同一请求体只改 `parameters.required`，每种各跑 3 次，结果完全一致）：

| `required` 取值 | 上游结果 |
| --- | --- |
| `null`（Codex 实发） | 400 `null is not of type "array"` |
| 字段缺失 | 400 同一个错 |
| `[]` | 200 |

### 本次未改动

- `api=responses` 的提供商仍按逐字节透传，不改写请求体。若这类中转同样做严格 schema 校验，`required: null` 仍会原样到达上游。
- 上游报错文案的兼容重试关键词表未调整。

## 验证

- 全量 Node 测试：233 项通过、0 项失败、1 项跳过（真实 `config.toml` 处于注入状态，跳过逐字还原比对）。
- 新增适配器用例覆盖：`required: null`、缺失 `required`、缺失 `properties`、chat 嵌套形状透传、`parameters: null`、`enum` 内的 `null` 保留。
- 端到端真实上游验证：用修复后的源码网关向出问题的中转发送修复前 100% 400 的 Codex 请求形状（单工具、namespace + custom 多工具、流式），共 6 次全部 200。

## 安装与升级

- Release 提供 Windows x64 NSIS 安装器、差分更新 blockmap 和自动更新元数据 `latest.yml`。
- 沿用仓库现有未签名构建流程，Windows 可能显示“未知发布者”或 SmartScreen 提示。
- 升级不清空用户配置、提供商、API Key 或历史使用量数据。
- 已安装的 gpt++ 会在启动约 8 秒后检查 GitHub Release，发现新版本仅弹窗提示，不会自动下载。
